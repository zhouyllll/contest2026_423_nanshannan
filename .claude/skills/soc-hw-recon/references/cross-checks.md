# 交叉验证手法

命中一份看起来对的 dtsi，和它确实是对的，是两回事。
**采用前至少做一项独立交叉验证** —— 用两个互不依赖的事实互相印证。

好的交叉验证有一个共同点：**它把两个不同来源的事实绑在一起**，
任一边错都会暴露。只在同一份文件内部自洽的检查没有价值。

## 1. GICR 长度 ↔ CPU 核数（ARM + GICv3，最有效）

```
GICR 区域长度 ÷ 0x20000 == CPU 核数
```

GICv3 给每个核一个 redistributor，跨距通常 `0x20000`。
dtsi 里 `interrupt-controller` 节点 `reg` 的第二段长度除以它，
应当等于 `cpus` 节点下 `cpu@` 的数量，也应当等于厂商标称的核数。

```sh
grep -A8 "interrupt-controller@" <dtsi> | grep "reg ="   # 取第二段长度
grep -c "cpu@" <dtsi>                                     # 核数
```

**这条同时验证了「中断控制器地址」和「核心配置」两个独立事实。**

> 实战：先选中的参考 dtsi 反推出 8 核，而厂商手册标称 4 核 ——
> 该条验证直接证伪了错误参考，改选后 4 核吻合。

## 2. GIC 版本 ↔ 端口能力

`compatible` 是 `arm,gic-v3` 还是 `arm,gic-400`(GICv2) 决定了
能否直接复用 `arch/arm64` 的 GICv3 通用实现。
同一厂商不同系列可能不同 —— 例如某厂商 s6 是 gic-v3 而 s7 是 gic-400。
**选参考 dtsi 时顺手确认这一项**，选错会导致中断整体不工作。

## 3. 外设地址 ↔ MMU 映射范围

所有要访问的外设基址必须落在 device 映射区间内：

```
DEVICEIO_BASEADDR <= 外设基址 < DEVICEIO_BASEADDR + DEVICEIO_SIZE
```

漏映射的表现是访问时直接取指/数据异常，**不是报错**。
把这条写进一致性校验脚本，每次改地址自动跑。

## 4. 总线偏移 ↔ 绝对地址

dtsi 节点名里的 `@xxxxx` 是**相对父总线**的偏移：

```
真实地址 = 父总线 ranges 的基址 + 节点 @ 偏移
```

验证方法：算出来的绝对地址应落在父总线 `ranges` 声明的长度范围内。
落在范围外说明取错了父节点。

## 5. 中断号 ↔ +32 偏移

dtsi 写 `<GIC_SPI n ...>`，实际中断号是 `n + 32`（SGI 16 + PPI 16）。
验证方法：算出的中断号应小于 `NR_IRQS`，且同一外设组的编号应连续
（如 uart0..uart4 通常是连号）。

## 6. 上板终验（唯一的真凭据）

前五条都是纸面推断的自洽性检查，**只能证伪，不能证实**。
真正的确认只有一条：板子上导出真实设备树逐项比对。

```sh
adb shell dtc -I fs -O dts /sys/firmware/devicetree/base > real.dts
```

拿到后与参考 dtsi diff，重点看 GIC、串口、内存三处。

## 什么不算交叉验证

- 「这份 dtsi 的文件名里有目标型号」—— 文件名不是事实
- 「厂商手册和 dtsi 都说是 4 核」—— 若手册正是选 dtsi 的依据，这是循环论证
- 「代码能编过」—— 地址是常量，填什么都能编过
