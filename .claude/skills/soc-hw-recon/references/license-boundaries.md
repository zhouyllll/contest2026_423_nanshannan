# 上游代码取用的许可证边界

openvela / NuttX 是 **Apache-2.0**。从 Linux 主线取硬件信息时，
**先看文件头的 SPDX 行再决定怎么用**。

## 分流表

| SPDX | 典型内容 | 处理方式 |
|---|---|---|
| `(GPL-2.0+ OR MIT)` | 多数厂商 dtsi、部分头文件 | **按 MIT 分支取用**，与 Apache-2.0 兼容。在文档中声明来源与所选分支 |
| `GPL-2.0` / `GPL-2.0-only` | 内核驱动 `.c`、多数子系统代码 | **不可复制**。只能阅读理解其描述的硬件行为，用自己的语言写成规格，再独立实现 |
| `BSD` / `MIT` 单一 | 少数工具与库 | 按其条款，通常可直接用 |

```sh
head -1 <file>       # SPDX 行永远在第一行
```

## 「读了但没抄」的边界在哪

可以提取的是**硬件事实**：

- 寄存器偏移与位定义
- 中断号、时钟频率、总线布局
- 硬件要求的操作时序（先复位再使能之类）

**不可复制的是表达**：

- 源代码本身（哪怕改了变量名）
- 代码的组织结构、函数切分方式
- 注释文字

判据：**如果换一个人拿着同一份硬件事实独立实现，写出来的结构可以完全不同，
那你的实现就应当是你自己的结构。**

## 建议的操作方式

1. 阅读上游驱动，**只记录寄存器语义**，整理成一份独立的规格文档
2. 规格文档里写明来源与许可证，以及「仅阅读理解、未复制代码」的声明
3. **对着规格实现**，不要对着原代码实现
4. 实现结构参照同项目内的同类驱动（例如 NuttX 里另一个简单 MMIO 串口），
   而不是参照 GPL 原驱动

这样做的额外好处：规格文档本身就是交付物，
比「一份能跑的驱动」更能体现工作深度，也方便他人复现。

## 需要向组织方确认的

若参赛/交付有源码审核环节，建议提前明确：

- 该参考方式的合规边界是否被接受
- 是否需要在交付文档中声明参考来源与实现方式
- 启动链路中的闭源二进制依赖（DDR 初始化固件之类）是否影响「开源交付」认定
