# 新 SoC 硬件参数勘察

适配一颗从未支持过的 SoC，第一难关**不是写代码，是「硬件长什么样」**。
驱动怎么写有现成模式（见 `nuttx-driver-development`），但基址、中断号、
时钟频率填什么，没有手册时就只能靠推断 —— 而推错的表现是
**上板没有任何输出、也没有任何报错**，是 bring-up 里最贵的一类返工。

本 skill 覆盖：**参数从哪来 → 怎么验证它是对的 → 怎么防止它被改漏。**

## 何时用

- 目标 SoC 在 openvela 和上游 Apache NuttX 里都没有端口
- 拿到的厂商文档是「用户手册」而非「硬件参考手册」（没有寄存器章节）
- 已经填了地址，但上板没输出 / 出乱码，需要分流定位

## 三步法

### 第一步：用指纹特征定位参考 dtsi

Linux 主线的 dtsi 是最好用的硬件参数来源 —— 上游合入、经过验证。
但同一厂商往往有十几份 dtsi，**选错就全盘皆错**。

用「CPU 核心型号 + 数量」作指纹去筛，通常唯一命中：

```sh
scripts/find-reference-dtsi.sh amlogic cortex-a510
```

指纹从哪来：厂商的用户手册/规格页通常会写核心型号与主频，
即使它不含任何寄存器信息。**这是用户手册在本流程中唯一但关键的作用。**

> ⚠️ 产品名对不上是常态。厂商常把同一颗 die 以不同系列名出货
> （AI/工业线 vs 影音线）。**按硬件特征匹配，不要按型号名匹配。**

### 第二步：交叉验证 —— 不验证就是猜

命中一份 dtsi 不等于它就是对的。**至少做一项独立交叉验证**再采用。

最有效的一条（ARM + GICv3）：

```
GICR 区域长度 ÷ 0x20000 == CPU 核数
```

它把「中断控制器地址」和「核心数量」两个独立事实绑在一起，
一次校验两边。更多手法见 `references/cross-checks.md`。

> 真实案例：某次先选中了核心型号相近的一份 dtsi，GICR 长度反推出 8 核，
> 而目标是 4 核 —— **正是这条验证证伪了错误的参考**，避免了整套地址填错。

### 第三步：许可证分流

上游代码不是都能用，也不是都不能用。**先看 SPDX 行再决定怎么用**：

| 授权 | 典型内容 | 怎么用 |
|---|---|---|
| `GPL-2.0+ OR MIT` | 多数厂商 dtsi | **按 MIT 分支直接取用**，与 Apache-2.0 兼容 |
| `GPL-2.0` 单一 | 内核驱动 `.c` | **只读懂硬件行为，用自己的话写成规格，再独立实现。不复制代码** |

寄存器偏移与位定义属于硬件接口事实，不构成驱动代码的著作权表达；
但**实现结构必须是自己的**。详见 `references/license-boundaries.md`。

## 要提取哪些参数

| 参数 | dtsi 里的位置 |
|---|---|
| GICD / GICR 基址 | `interrupt-controller` 节点 `reg` 的两段 |
| 外设基址 | 各节点 `reg` + **父总线 `ranges` 的偏移**（★ 易漏，见下） |
| 中断号 | `interrupts = <GIC_SPI n ...>` → **实际中断号 = n + 32** |
| 触发方式 | 同上第三个字段，`EDGE` 与 `LEVEL` 的中断处理写法不同 |
| 时钟频率 | `clocks` 指向的 `fixed-clock` 节点的 `clock-frequency` |
| DDR 与保留区 | 板级 dts 的 `memory@` 与 `reserved-memory` |
| 镜像加载地址 | **不在 dtsi**，在 U-Boot 的 `include/configs/<soc>_common.h` 的 `kernel_addr_r` |

> ★ **总线偏移必须叠加。** dtsi 里写 `serial@7a000` 是**相对父总线**的偏移，
> 真实地址 = 父总线 `ranges` 的基址 + 该偏移。直接拿 `@` 后面的数字当基址
> 是高频错误。

## ★ 地址类静默失效

同一个地址往往散落在多个文件，**没有任何机制保证它们同步，改漏一处不报错**。

典型的两组：

```
镜像加载地址（3 处）  chip.h 的 LOAD_BASE
                      defconfig 的 RAM_START
                      链接脚本的起始地址
调试串口基址（2 处）  C 侧宏定义
                      汇编 early print 的字面量（汇编取不到 C 宏，只能写死）
```

**对策：写一个一致性校验脚本，并对它做反向验证**（故意改错一处，
确认脚本真的返回非零）。一个永远返回通过的检查脚本比没有更糟。

顺带校验：所有外设基址都必须落在 MMU 的 device 映射范围内，
否则访问时直接异常而不是报错。

## 上板终验：走 ADB 比等原理图快

多数开发板出厂带 Linux 且默认开启 ADB。板子到手第一件事：

```sh
adb shell
dtc -I fs -O dts /sys/firmware/devicetree/base   # 真实设备树，一次性终验全部推断
cat /proc/cpuinfo                                 # 核心型号与数量
cat /proc/cmdline                                 # console= 直接给出调试串口与波特率
cat /proc/iomem /proc/interrupts                  # 地址与中断的运行时视图
```

**但串口物理通路仍须单独验证** —— ADB 通只说明 USB/网络通，
不代表串口接线对。M1 的观测手段是串口，必须先用出厂固件确认它本身可靠。

## 排查分流

| 现象 | 指向 |
|---|---|
| 完全没输出、也没报错 | 加载地址错、调试串口选错路、MMU 没映射到 |
| **出字符但是乱码** | 时钟频率或分频系数错。**这是好消息** —— 启动链路、内存映射、异常向量已全通，只差串口参数 |
| 打印到某处停住 | MMU 漏映射某段，或中断没挂上 |
| 能进 shell 但内存不对 | DDR 容量取值错 |

## 反面教训

- **别按型号名找参考**，按硬件特征找。产品名与 die 常常不是一一对应。
- **别跳过交叉验证**。命中一份看起来很像的 dtsi，和它就是对的，是两回事。
- **别把用户手册当硬件手册**。前者给核心型号和外设清单，后者才有寄存器。
  拿到文档先 grep 一次 `寄存器`/`register`/`内存映射`，零命中就别指望它。
- **分频系数常常分 SoC 变体**。同一系列的早期与后期型号可能用不同的分频，
  取错的表现是乱码。这类「同一驱动内按 compatible 分支」的差异必须查清。
