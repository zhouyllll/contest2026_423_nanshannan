# 板级时钟排查

时钟错误在 bring-up 里占的比重远超它应得的份额，因为它**几乎不报错**。
寄存器照样读写、驱动照样返回成功、上层照样拿到数据 —— 只是频率不对。
更糟的一种是**整条链一起错、彼此还自洽**，那时连"数据不对"都看不出来。

本 skill 覆盖：时钟有哪几层 → 每层怎么单独证伪 → 怎么拿到"地面真值"。

## 何时用

- 外设的寄存器读写完全正常，但总线上没有波形、引脚上没有信号
- 速率类参数对不上：波特率乱码、音频音调不对、帧率偏低
- 实测速率是期望值的**整数倍或整数分之一**（2、4、8…）—— 这是分频错的指纹
- 无线/组合模组怎么都不上电（多半缺的是 32.768kHz，不是主时钟）

## 时钟不是一层，至少是四层

排查必须逐层证伪，跳层就会得出"时钟是好的"这种错误结论。

| 层 | 内容 | 配错的表现 |
|---|---|---|
| 1. 总线时钟 | PCLK / HCLK，**只管寄存器访问** | 读寄存器回 0 或全 f、访问挂总线 |
| 2. 功能时钟门控 | 驱动 SCL / SCLK / 采样的那一路 | **寄存器一切正常，引脚上没有任何波形** |
| 3. 分频与选源 | mux 选哪个父时钟、除多少 | 频率错，但一切"工作" |
| 4. 板级外给时钟 | 晶振、另一颗芯片的 CLKOUT | 外设根本不启动 |

> ★ **第 1 层和第 2 层是两回事，这是最贵的一个坑。**
> 很多驱动的初始化自检是"往某个寄存器写值再读回，一致就算活着" ——
> 那只验证了 PCLK。功能时钟被门控时，这个自检**照样通过**，而设备是死的。
>
> 真实案例：I2C 驱动扫描全空，CLKDIV 写回自检通过。真因是
> `clk_i2c2` 功能时钟没使能，SCL 上没有任何波形。判据要用**传输计数器**
> （`FCNT`）这类"证明信号真的出去了"的寄存器，不能用寄存器回读。

## ★ 设备树写的是意图，不是现状

这是本 skill 最想讲的一条。

```
assigned-clocks       = <&mclkout_sai1>;
assigned-clock-rates  = <12288000>;
```

这两行的意思是"**Linux 的时钟框架启动时会去把它设成 12.288MHz**"。
它**不是**上电后的硬件现状，也**不是**引导器留下的值。

在裸机/RTOS 上你没有那套时钟框架。如果你只照着 dtb 把**门控**打开、
以为频率就是 `assigned-clock-rates` 写的那个值 —— 你拿到的是引导器
留下的任意值。

> ★ **而且这两行往往不在你正在移植的那个外设节点上。**
>
> 上面这段实际出现在 **es8388 编解码器**节点里，它引用的是
> `mclkout_sai1`。提供时钟的 `sai1` 节点自己只有
> `clocks = <&cru MCLK_SAI1_8CH>, <&cru HCLK_SAI1_8CH>` —— 一个频率
> 要求都没有。**频率约束挂在消费者一侧，只读提供者节点必然漏掉。**
>
> 所以查的时候要反过来搜：先拿到时钟名（`mclkout_sai1`），再全树搜谁
> 引用了它。

> 真实案例：SAI 音频链路。我们只调了三个 `clk_gate()`，从没写过分频。
> 实测 MCLK 是 **3.072MHz**，正好是 12.288MHz 的 1/4。
>
> 致命的是它**没有报错**：编解码器配的是 256fs，3.072M / 256 = 12kHz，
> 于是 SAI 的帧率、编解码器的采样率、上层请求的 48kHz 三者"各自都对"，
> 整条链自洽地跑在 12kHz 上。放音能响、录音有数据，只是全部慢 4 倍 ——
> 没有任何一层会报错，因为每一层内部都是一致的。

**对策**：凡是 `assigned-clock-*` 出现的地方，都当成"这里有一个必须由
我自己设的分频"，并在代码里**读回确认**，而不是假定。

## 怎么拿到地面真值

频率是唯一能被"测"出来的东西 —— 只要找一个**由时钟驱动、且能被墙钟
观测**的可数量。别去推导，去测。

| 手段 | 做法 |
|---|---|
| **FIFO 填充速率** | 开着外设不取数，按固定间隔采样 FIFO 水位。涨得多快就是实际数据率 |
| 传输计数器 | 很多控制器有 `*_DATA_CNT`，配合墙钟取两次差值 |
| 分频寄存器反推 | 读回实际的 mux/div，乘回父时钟 —— 但父时钟本身也要这样验，别停在第一层 |
| 定时器/PWM 输出 | 配一个已知分频，示波器或 GPIO 中断计数 |

> 真实案例：SAI 的 RX FIFO 按 100µs 采样 11 次，水位走 `0 1 2 4 5 6 7 8 9 11 12`
> —— 1000µs 涨 12 个字，即 12000 帧/秒。期望 48000。**1/4 这个干净的比值
> 直接指向分频，而不是指向"数据没来"。**
>
> 注意先排除测量工具本身：`up_udelay()` 之类若不准，同样会得到 1/4。
> 先确认延时函数走的是硬件计数器而非标定循环。

## 整数比值 → 直接查分频

实测速率与期望值之比若是干净的 2/4/8/16 或其倒数，**几乎一定是分频或
位宽，不是"数据丢了"**。按这个顺序查：

1. 父时钟选错（mux 指向了另一个 PLL）
2. 分频系数没设（用了复位默认值）
3. 分频寄存器的编码是 `n-1` 还是 `n`（差一倍最常见的来源）
4. 每帧的位数算错（声道数 × 位宽），它和分频是乘在一起的

> 分频寄存器几乎都是 `((n) - 1) << shift` 的编码，而门控和选源不是。
> 同一个头文件里混着两种约定，抄的时候极易带错。

## 板级外给时钟：看原理图，不看设备树

第 4 层的信息**不在 dtb 里**。dtb 描述的是"Linux 打算怎么用这块板子"，
不是"这块板子怎么连"。某个 pinctrl 组没有任何节点引用，只说明 Linux
侧没走时钟框架 —— **推不出硬件上没有这条连接**。

> 真实案例：WiFi/蓝牙组合模组死活不上电，电源、复位、引脚、时序全部
> 逐条验证正确。dtb 里 `clk0_32k` 没有任何节点引用，于是我判断"模组自带
> 晶振"。原理图给出的事实是：
>
> ```
> HYM8563 (RTC)  32KOUT_RTC → WIFIBT_32KIN_2T2R
> ```
>
> 模组的 32.768kHz 由那颗 RTC 提供，而 RTC 的 CLKOUT 需要显式使能
> （寄存器 0x0D，bit7 = 输出使能）。组合芯片没有 32k 低频时钟就无法
> 完成上电 —— 这一条同时解释了 SDIO 与蓝牙两个方向的失败。

还有一条同样代价高的：**注释写了不等于代码做了**。那份 I2C 文件顶部
早就写着"同时给 WiFi 供 32.768kHz"，知识在仓库里躺了很久，代码从来
没写。排查时读到注释就认定"这个已经做了"，会把真正的缺口跳过去。

## 改完时钟要握手

不少控制器（DW MMC、部分 SDHCI、某些音频控制器）改分频后**必须发一条
"更新时钟"命令**，新分频才生效。写完寄存器读回是对的，但硬件仍在用旧值。

典型序列：关时钟使能 → 改选源 → 改分频 → 开时钟使能，**每一步后面都跟
一次更新命令**。少一次，现象是"寄存器都对，就是不工作"。

## 排查分流

| 现象 | 指向 |
|---|---|
| 寄存器读回 0 / 全 f / 挂总线 | 第 1 层：PCLK/HCLK 门控没开 |
| 寄存器正常，引脚无波形，传输计数器恒 0 | 第 2 层：功能时钟门控没开 |
| 能工作但速率是整数倍/分之一 | 第 3 层：选源或分频 |
| 外设/模组完全不响应，电源复位都对 | 第 4 层：缺板级外给时钟（常是 32.768kHz） |
| 上层无报错，但数据"慢/快了整倍数" | 整条链自洽地跑错频率 —— 必须实测 |

## 反面教训

- **别拿寄存器回读当"时钟通了"的判据。** 它只证明 PCLK。
- **别把 `assigned-clock-rates` 当现状。** 那是 Linux 的目标值；裸机上
  没人替你去设。
- **别在"数据没来"这个方向上深挖整数比值。** 1/4 就是分频，不是丢包。
- **别信 dtb 的电路连接。** 连接看原理图，dtb 只说软件打算怎么用。
- **别信注释。** 注释记录意图，只有代码是事实。
