# 怎么测出时钟的"地面真值"

推导会错，测量不会。本文列出在没有示波器时，纯靠软件拿到实际频率的手法。

## 原则：找一个由该时钟驱动、且能被墙钟观测的可数量

时钟本身看不见，但它驱动的东西留下了可数的痕迹。任选其一即可：

| 可数量 | 适用外设 | 换算 |
|---|---|---|
| FIFO 水位增长 | 音频、SPI、UART、CSI | Δ水位 / Δ时间 = 数据率 |
| `*_DATA_CNT` 计数器 | 很多 Rockchip/DW 控制器有 | 两次差值 / Δ时间 |
| 中断次数 | 定时器、帧中断 | 次数 / Δ时间 |
| DMA 残余量 | 任何走 DMA 的外设 | 已搬字节 / Δ时间 |
| GPIO 翻转计数 | 把时钟引到 GPIO 并采样 | 见下"采样法" |

## 采样法的两个前提

**一、先验证你的延时函数。**

如果用 `up_udelay()` / `udelay()` 这类忙等来控制采样间隔，**它本身可能不准**。
标定循环式的实现（按 CPU 频率算圈数）在变频、多核、编译器优化下误差很大；
基于硬件计数器的实现才可信。

> 这一点很要命：延时函数慢 4 倍和时钟快 4 倍，观测到的现象**完全一样**。
> 先确认 `up_udelay` 走的是 arch timer / 系统计数器，再相信采样结果。
> 查法：找 `up_ndelay` 的实现，看它是查硬件计数器还是跑空循环。

**二、采样期间不要取数。**

测 FIFO 填充速率时，只读水位寄存器，**不要读数据寄存器** —— 一边填一边
取，测到的是两者之差，不是填充速率。

## 一个可直接抄的例子

```c
/* 开着接收但不取数，按 100us 采样 11 次水位 */
uint32_t traj[11];
for (int k = 0; k < 11; k++)
  {
    traj[k] = getreg32(BASE + FIFO_LEVEL) & LEVEL_MASK;
    up_udelay(100);
  }
syslog(LOG_INFO, "水位/100us %lu %lu %lu ...\n", traj[0], traj[1], ...);
```

实测输出 `0 1 2 4 5 6 7 8 9 11 12`：1000µs 涨 12 个字 → 12000 帧/秒。
期望 48000 → **比值 1/4，干净的整数比，直接指向分频**。

> 如果轨迹是 `0 0 0 0 ...` 恒为 0，那才是"数据没来"（时钟没输出、
> 外设没启动、引脚没复用对）。**能涨但涨得慢，和完全不涨，是两类问题。**
> 这条轨迹一次把两者分开了 —— 这正是它值得写的理由。

## 整数比值对照

| 实测/期望 | 最可能的原因 |
|---|---|
| 1/2 或 2 | 分频寄存器的 `n` vs `n-1` 编码搞反 |
| 1/4 或 4 | 选错父时钟；或声道数×位宽算错了一半再叠加分频 |
| 1/8、1/16 | 复位默认分频（很多 CRU 的复位值是最大分频） |
| 非整数但接近 | 父时钟是小数分频（frac divider），需要按小数分频器算 |

## 别忘了反向确认

测出来改完之后，**再测一次**。改分频寄存器不生效的情况很常见：

- 需要额外的"更新时钟"握手命令（DW MMC、部分音频控制器）
- 写的是影子寄存器，要触发生效
- Rockchip 这类带写使能掩码的寄存器：高 16 位必须置对应的 mask 位，
  否则写入被硬件忽略，**读回还是旧值**
