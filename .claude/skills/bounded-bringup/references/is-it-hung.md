# 板子"没反应"时的分流

串口读不到东西**不是一个诊断**。至少四种成因，处理方式完全不同。

## 第一步：分清四种

| 观测 | 成因 | 下一步 |
|---|---|---|
| 0 字节，回车无回显 | 挂死 / 饿死 / 进了下载模式 | 看 USB 枚举 |
| 有日志滚动，但无回显 | 前台程序占着控制台，系统是活的 | 等它结束，或想办法中断 |
| 持续刷屏（转圈动画等） | 引导器在等下载；或某循环在刷 | 直接烧写，别等"空闲" |
| 乱码 | 系统在跑，串口参数不对 | 查时钟/分频/波特率 |

## USB 枚举是区分"挂死"和"下载模式"的关键

```sh
lsusb | grep -i "2207\|rockchip"     # Rockchip 的 VID
```

- **有**该设备 → 板子在下载模式，活着，可以直接烧写
- **没有**任何设备 → 真挂了，需要物理复位

这一步很便宜，但省掉它就会把"正等着被烧写"误判成"板子死了"。

## ⚠ 排空逻辑的陷阱

很多串口辅助脚本这样写：

```python
def drain(s, idle):
    last = time.time()
    while time.time() - last < idle:   # 连续 idle 秒没有新字节才算就绪
        d = s.read(4096)
        if d: last = time.time()
```

板子如果在**无限刷屏**，这个循环永远不会退出，脚本超时后你会得到
"板子没反应"的错误结论 —— 而它其实活得好好的。

**对策**：给 drain 一个总时长上界（又是"整件事有上界"），
并在超时时打印**收到的字节数和最后 200 字节**，而不是只说超时。
有没有字节、字节长什么样，直接把四种成因分开。

## 饿死 vs 崩溃

两者都表现为"0 字节、无回显"，但成因完全不同：

| | 崩溃 | 饿死 |
|---|---|---|
| 原因 | 异常 / 断言 / 跑飞 | 高优先级线程长时间不让出 CPU |
| 特征 | 通常**之前**会有异常打印（除非打印链路本身就是受害者） | 最后一条日志是正常业务日志，戛然而止 |
| 复现 | 每次都在同一点 | 与负载/时长相关 |
| 修法 | 查异常原因 | 缩短忙等、降优先级、改用让出 CPU 的等待 |

> 判断线索：**最后一条日志是什么**。如果它是一条正常的业务日志，而且
> 紧跟着就该有下一条 —— 更可能是饿死。崩溃通常会留下点什么，除非
> 崩的就是输出路径本身。

## 恢复成本排序

先试便宜的：

1. 等一等（可能只是慢）
2. 发 `Ctrl-C`（前台程序可能可中断）
3. 看 USB 枚举 → 在下载模式就直接烧
4. 物理复位
5. MASKROM / 救砖流程 ← 把未验证流程放进启动路径的代价

**设计时就该让故障停在第 3 步以内。** 第 5 步意味着启动路径里有
没验证过的东西 —— 那是设计问题，不是运气问题。
