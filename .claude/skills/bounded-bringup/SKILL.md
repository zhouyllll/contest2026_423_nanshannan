# 有界的 bring-up

在有调试器、有 `Ctrl-C`、有 `kill` 的环境里，"卡住了"是小事。
在一块只有一根串口线的板子上，**卡住 = 物理复位 = 一轮几分钟的返工**，
而且卡住时你什么信息都拿不到 —— 恰恰是最需要信息的时刻。

本 skill 讲三件事：**上界界在哪 → 卡住了怎么分辨 → 什么不能放进启动路径。**

## 何时用

- 写自检命令、诊断探针、任何"跑一次看看硬件活没活"的东西
- 驱动里要等一个硬件事件（FIFO、中断、握手、完成标志）
- 板子跑完某个命令串口就没反应了，需要判断发生了什么
- 准备把一段还没验证过的硬件初始化加进 `board_app_initialize` 之类

## ★ 上界要界在"整件事"上，不是界在每一次等待上

这是本 skill 的核心，也是我在同一个项目里**犯了四次**的错误。

逐次有界 **不等于** 总量有界：

```c
/* 看起来很有界：每个字最多等 200ms */
for (i = 0; i < 2048; i++)
  {
    if (wait_one_word(200 /* ms */) < 0) break;
    buf[i] = read_word();
  }
/* 实际最坏：2048 x 200ms ≈ 409 秒。等于没有上界。 */
```

正确的写法是给**整个操作**一个预算，每次等待从预算里扣：

```c
int budget_us = TOTAL_BUDGET_US;

while (got < want && budget_us > 0)
  {
    if (data_ready()) { buf[got++] = read_word(); continue; }
    up_udelay(STEP_US);
    budget_us -= STEP_US;
  }
/* 到点就带着已经拿到的部分返回，并如实报告拿到了多少。 */
```

### 四次犯错的样子（都是同一个错误换皮）

| # | 写法 | 为什么不算有界 |
|---|---|---|
| 1 | 直接用现成的前台播放/录音程序做验证 | 它本来就是阻塞的，一卡就把控制台带走 |
| 2 | 自检命令按**字节数**设上界："收够 5 秒数据就停" | 只在缓冲区**会回来**时成立。一个都不回来时 `mq_receive` 永远阻塞 |
| 3 | 改用 `mq_timedreceive`，每次等 2 秒 | 只要每次都还回**一点点**数据，循环就一直"有进展"，凑够总量可以跑几小时 |
| 4 | 驱动里每个字设 200ms 上界 | 2048 个字 → 409 秒 |

> **"有界"要界在等待上，不是界在期望的产出上。**
> 我写第 2 版的动机就是"别人的程序会卡"，结果把同一个洞留在了同一个位置。

## ★ 上界的数值要贴着物理时间，不能拍一个大数

给对了位置还不够。一个"安全的大数"会带来另一种死法。

> 真实案例：接收一个缓冲区，我给了 1 秒预算 —— 确实是上界。但这段代码
> 跑在编解码器的工作线程里，优先级是 `SCHED_FIFO` 最高 -3，而循环体是
> `up_udelay()` **忙等**。47 个缓冲区 × 1 秒 = 47 秒的高优先级忙等，
> 控制台输出线程一次都排不上。
>
> 现象：串口全哑，`Ctrl-C`、回车都是 0 字节。**看起来完全像崩溃，
> 其实是饿死。**

预算应该从"这批数据本来需要多久"算出来：

```c
/* 2048 帧 @ 48kHz = 42.7ms，给 2 倍 */
budget_us = (uint64_t)frames * 2 * 1000000 / samplerate;
if (budget_us < MIN_US) budget_us = MIN_US;
if (budget_us > MAX_US) budget_us = MAX_US;
```

这样它对系统的占用特征，和已经能正常工作的那条路径一致。

> 附带一条：**在高优先级线程里忙等，本身就是设计问题。** 能让出 CPU 就
> 让出（`nxsig_usleep`/信号量/中断回调）。忙等只在"等待时间 < 一次调度
> 往返"时才划算。

## 串口没反应，有四种完全不同的原因

"看起来没输出"不是一个诊断，是四个。分不开就会在错误的方向上深挖。

| 观测 | 含义 | 怎么确认 |
|---|---|---|
| 读到 **0 字节**，回车也无回显 | 真的挂了 / 饿死 / 进了下载模式 | 看 USB 枚举：有 Rockchip 类设备 = 下载模式；没有 = 挂了 |
| 有日志输出但**无回显** | 前台程序占着控制台，系统是活的 | 日志还在滚就是活的 |
| **持续刷屏**（如 `\|/-\` 转圈） | 引导器在等下载，或某个循环在刷 | 这种情况下"等空闲再发命令"的脚本会永远等不到 |
| 输出**乱码** | 系统在跑，只是串口参数不对 | 这其实是好消息：启动链路全通 |

> 第三种坑过我一次：排空逻辑写成"连续 N 秒没有新字节才算就绪"，
> 而板子在无限刷转圈动画 —— 脚本超时退出，我判定"板子死了"，
> 实际上它正停在下载模式等着被烧写。

## 不要把未验证的硬件流程放进启动路径

一段还没验证过的初始化（固件加载、PHY 上电、DMA 启动）如果挂在
`board_app_initialize` 之类的启动路径里，它一挂 **系统就起不来**，
于是你连改回去的机会都没有 —— 只能走 MASKROM / 救砖流程。

**规则**：新硬件的 bring-up 一律先做成**手动触发的命令**。
只有在它连续多次成功之后，才考虑移进启动路径。

同理，**自动化脚本不要替用户"顺手多做一步"**。把"可恢复"变成
"不可恢复"的往往就是那一步好意。

## 自检命令的最小骨架

```c
/*  1. 所有参数从命令行来，给保守的默认值
 *  2. 整体墙钟上界：deadline = now + f(请求量)
 *  3. 每一步的等待都用 timed 版本（mq_timedreceive / sem_timedwait）
 *  4. 每一轮循环开头检查 deadline，到点就 break
 *  5. 失败时打印**观测到的数值**，不是"失败了"
 *  6. 无论成功失败都走同一条清理路径（关设备、释放缓冲区）
 *  7. 结论用阈值给出判定：静默 / 偏弱 / 正常
 */
```

第 5 条最容易省掉，也最贵：`printf("初始化失败\n")` 和
`printf("初始化失败 STATUS=0x%08x FIFO=%u\n", ...)` 之间，
差的是下一轮要不要再烧一次板子。

## ⚠ 诊断宏可能被编译期关掉

`dmaerr()` / `auderr()` / `wlerr()` 这类子系统日志宏，在对应的
`CONFIG_DEBUG_*` 没开时**展开成空**。你以为在等一条错误信息，
它根本不可能出现。

> 真实案例：我连着几轮在等一条 `audwarn("只收到 %zu/%zu 字")`，
> 而 `CONFIG_DEBUG_AUDIO` 从头到尾就没开过。

**规则**：初始化、探针、失败路径这类**单次执行**的地方，
直接用 `syslog(LOG_ERR/LOG_INFO, ...)`，不要用子系统宏。
热路径才需要考虑用可关闭的宏。

## 反面教训

- **别用"期望的产出"当上界。** 产出不来时它就不成立。
- **别拍一个"安全的大数"。** 上界要贴物理时间，否则换一种死法。
- **别在高优先级线程里长时间忙等。** 饿死看起来和崩溃一模一样。
- **别把"看起来没输出"当成一个结论。** 它至少有四种成因。
- **别把没验证过的硬件流程放进启动路径。** 代价是整块板子。
- **别等一条可能被编译掉的日志。**
